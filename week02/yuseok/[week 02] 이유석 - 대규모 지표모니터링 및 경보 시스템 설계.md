# 🏗️ 대규모 지표 모니터링 및 경보 시스템 설계 PR


## 1. 도메인 배경 및 핵심 개념

여러 고객이 자기 서버의 상태를 대시보드에서 확인하고, 문제가 생기면 알림을 받을 수 있는 서비스를 설계했습니다.

고객 서버가 사설망에 있으면 외부에서 접근하기 어렵습니다. 그래서 고객 내부에 수집기를 두고, 수집기가 서버에서 지표를 가져와 SaaS로 보내도록 했습니다.
| 개념 | 의미 |
| --- | --- |
| 테넌트 | 서비스를 사용하는 고객입니다. 여러 고객의 지표를 같은 DB에 저장하므로 tenant_id로 어느 고객의 데이터인지 구분합니다. |
| 시계열 데이터 | 시간에 따라 기록한 측정값입니다. 예를 들어 web-01 서버의 CPU 사용률을 측정 시각과 함께 저장합니다. 서버 이름이 같아도 고객이 다르면 별도로 저장합니다. |
| 경보 규칙 | 언제 알림을 보낼지 정합니다. 예를 들어 CPU 사용률이 90%를 넘는 상태가 5분 동안 이어지면 경보를 보내고, 정상으로 돌아오면 복구 알림을 보냅니다. |

## 2. 요구사항 및 설계 범위

### 기능적 요구사항
- 데이터 보관 기간은 1년
- 고객별로 지표 전송 토큰을 발급하고, 지표를 받을 때 토큰을 확인합니다.
- 서버의 CPU 사용률, 메모리 사용량, 요청 수를 수집하고 저장합니다.
- 사용자는 대시보드에서 자기 고객사의 지표를 서버와 시간 범위별로 조회할 수 있습니다.
- 고객별로 경보 조건과 알림 수신자를 설정할 수 있습니다. 경보가 발생하거나 복구되면 이메일, 문자, 웹훅으로 알립니다. 지표가 들어오지 않는 경우는 정상 상태와 구분합니다.

### 비기능적 요구사항
- 규모 확장성 : 고객사와 서버가 늘어나면, 증가하는 지표와 경보를 처리할 수 있도록 수집·저장·알림 처리 용량을 늘릴 수 있어야 합니다.
- 낮은 응답 지연 : 사용자는 대시보드에서 지표를 빠르게 조회할 수 있어야 합니다. 경보 평가에 필요한 조회도 평가 주기 안에 처리할 수 있어야 합니다.
- 고객사별 데이터 격리 : 각 고객사는 자기 회사의 지표와 경보 설정에만 접근할 수 있어야 합니다. 경보 알림도 해당 고객사가 설정한 수신자에게만 전달되어야 합니다.
- 고객사별 부하 격리 : 한 고객사의 지표 전송이나 조회 요청이 몰려도 다른 고객사의 수집·조회·경보 평가에 미치는 영향을 줄여야 합니다. 이를 위해 고객사별 수집량, 조회 기간, 동시 조회 수를 제한합니다.
- 장애 복구 : DB나 알림 작업자가 잠시 중단되면 이미 받은 지표와 경보 이벤트를 보관했다가 복구 후 다시 처리할 수 있어야 합니다. 알림 전송에 실패한 경우에는 재시도할 수 있어야 합니다.

### 설계 가정
여러 고객이 하나의 모니터링 서비스를 사용한다고 가정합니다. 고객의 사설망 안에 수집기를 설치할 수 있습니다.
고객은 처리 자원과 저장소를 공유하며, 지표와 경보 설정은 고객별로 구분합니다.

설계는 지표 수집·저장·조회, 대시보드, 경보 평가와 알림 전송을 다루고, 로그·트레이스 수집과 과금은 범위에서 제외합니다.
| 상황 | 트래픽 특성 | 설계에 집중할 부분 |
| --- | --- | --- | 
| 일반적인 상황| 고객의 수집기에서 지표가 꾸준히 들어온다. | 지표 저장, 조회 성능, 고객별 정보 격리 | 
| 요청이 몰리는 상황 | 여러 수집기의 전송 시점이 겹치며 지표가 한꺼번에 들어옵니다. | kafka에 지표를 두고 처리하는 방법, 조회 부하가 다른 고객들에게 미치는 영향, 알림 전송의 지연 |

### 설계 설명

### A. 지표를 모아 시계열 DB에 저장하기 

Agent는 서버에 주기적으로 요청해 CPU 사용률이나 메모리 사용량 같은 지표를 가져옵니다(풀). 이렇게 모은 지표를 고객별 전송 토큰과 함께 모니터링 서비스의 수집 API로 보냅니다(푸시).

수집 API는 토큰을 확인한 뒤 토큰에 연결된 고객 ID를 지표에 붙여 Kafka에 기록합니다. 여러 고객이 지표를 한꺼번에 보내면 Kafka에 지표가 잠시 쌓입니다. 
저장 작업자는 처리할 수 있는 만큼 Kafka에서 지표를 읽어 시계열 DB에 저장합니다. 

### B. 대시보드에서 지표 조회하기

사용자가 서버와 조회 기간을 선택하면 대시보드가 질의 서비스로 요청을 보냅니다. 질의 서비스는 로그인한 사용자의 소속과 권한을 확인한 뒤 조회 권한이 있는 고객의 지표만 시계열 DB에서 가져옵니다. 
대시보드는 이 지표를 그래프로 보여 줍니다. 
### C. 경보 평가와 알림

경보 평가기는 관계형 DB에서 고객별 규칙과 현재 경보 상태를 읽습니다. 질의 서비스에서 해당 고객의 최근 지표를 가져와 규칙과 대조합니다. 
경보가 처음 발생하거나 정상으로 돌아왔을 때만 발송 대기 테이블에 알림을 등록합니다. 경보 상태 변경과 알림 등록은 같은 트랜잭션으로 처리합니다. 

알림 작업자는 발송 대기 테이블을 주기적으로 확인합니다. 고객의 수신자 설정에 따라 이메일, 문자 또는 웹훅으로 알림을 보냅니다. 전송에 실패하면 다시 시도합니다. 

## 4. 기술 선택 근거

### Prometheus Agent 모드
고객 서버가 사설망에 있어서 내부에 수집기를 두었습니다. 지표 조회와 경보 판단은 모니터링 서비스에서 합니다. 
수집기에는 CPU 사용률이나 메모리 사용량을 주기적으로 가져와 수집 API로 보내는 기능에 집중하는 Prometheus Agent 모드를 선택했습니다.

### 지표 수집용 Kafka
여러 고객이 동시에 지표를 보내면 DB에 쓰기 요청이 몰릴 수 있습니다. 
지표는 Kafka에 먼저 넣어 두고 저장 작업자가 처리할 수 있는 만큼 읽도록 했습니다. 
DB가 잠시 멈춰도 복구된 뒤 Kafka에 남은 지표를 읽어 저장할 수 있습니다.

### 알림 발송 대기 테이블
처음에는 알림도 Kafka로 보내려고 했습니다. 지표와 알림이 같은 클러스터를 쓰면 Kafka가 멈췄을 때 이미 발생한 알림도 보내기 어렵습니다. 
알림용 Kafka를 따로 두는 방법도 검토했습니다. 알림 작업자만 이벤트를 읽는 지금 구조에서는 클러스터를 하나 더 운영하는 게 부담이라고 봤습니다.

경보 상태를 저장하는 관계형 DB에 발송 대기 테이블을 추가했습니다. 경보가 발생하거나 복구되면 상태 변경과 보낼 알림을 같은 트랜잭션으로 저장합니다. 
알림 작업자는 테이블에서 대기 중인 알림을 읽어 보내고 실패하면 다시 시도합니다. 지표용 Kafka가 멈춰도 DB에 들어 있는 알림은 계속 보낼 수 있습니다.

### 시계열 DB
대시보드에서는 서버 한 대의 최근 한 시간 CPU 사용률처럼 특정 기간의 지표를 자주 조회합니다. 
경보를 평가할 때도 최근 몇 분 동안의 지표를 읽어야 합니다. 서버별 지표를 시간 범위로 읽는 일이 잦아서 시계열 DB를 선택했습니다.


## 5. 트레이드오프

### Prometheus Agent 모드
고객 내부 수집기는 지표를 가져와 보내는 역할만 맡습니다. 조회와 경보 평가는 모니터링 서비스에서 하기 때문에 고객마다 조회나 경보 설정을 따로 관리하는 부담이 줄어듭니다.
하지만 고객과 모니터링 서비스 사이의 연결이 끊기면 수집기에 지표를 잠시 보관해도 새 지표를 바탕으로 한 경보는 늦어질 수 있습니다. 

### 지표 수집용 Kafka
여러 고객이 지표를 한꺼번에 보내도 Kafka에 잠시 쌓아 두면 저장 작업자가 처리할 수 있는 만큼 읽을 수 있습니다. 지표가 많이 쌓이면 대시보드에 최신 값이 늦게 반영됩니다.
그래서 Kafka의 남은 저장 공간과 지표가 DB에 저장되기까지 걸리는 시간을 확인해야 합니다. 

### 알림 발송 대기 테이블
경보 상태와 보낼 알림을 같은 DB에 저장하면 상태만 바뀌고 알림이 바뀌고 알림이 빠지는 일을 막을 수 있어 지표용 Kafka가 멈춰도 DB에 이미 저장된 알림은 계속 보낼 수 있습니다.

대신 알림 작업자가 대기 테이블을 주기적으로 읽어서 DB에 부하가 생깁니다. 경보 DB가 멈추면 대기 중인 알림도 읽을 수 없습니다.
알림 전송에 성공했더라도 결과를 기록하기 전에 작업자가 멈추면 재시도할 때 같은 알림이 다시 나갈 수도 있습니다.
