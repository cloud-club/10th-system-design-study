이걸 B2B 구독 서비스로 운영하면 세 가지가 핵심 과제가 됩니다. 첫째 루프로 인한 비용 폭주, 둘째 고객사 자체 키(BYOK)와 공용 키 사후 청구의 공존, 셋째 사내 기밀 유출과 권한 상승을 막는 보안 감사입니다.

실행 단위와 요청 처리 흐름

단위 1 세션 (대화방)

사용자가 이어가는 전체 대화 문맥의 묶음입니다.

단위 2 턴 (사용자 질문 1회)

질문 한 번에 대한 전체 추적(Trace) 단위입니다.

단위 3 스텝 (개별 LLM 호출과 도구)

한 턴 안에서 LLM 호출과 도구 실행이 여러 번 반복됩니다.

1. 인증과 입력 검사개인정보와 악성 프롬프트를 먼저 차단
2. 진입 사전 확인잔액 소진 계정을 빠르게 차단 (Fail-fast)
3. Agent 실행 루프 (목표 달성까지 반복)
3a. LLM 호출키 선택 후 호출별 예산 예약
3b. 도구 실행본인 권한 확인 및 결과물 검사
3c. 상태 저장단계별 저장 및 승인 대기
4. 출력과 스트리밍민감정보 검사 후 글자 단위 실시간 전송 (SSE)
5. 추적과 과금개별 LLM 호출 단위로 비동기 집계

흐름에서 두 가지를 강조하겠습니다. 첫째, LLM 게이트웨이 호출(3a)은 루프 뒤에 오는 게 아니라 Agent 루프 안에서 도구 실행(3b)과 반복됩니다. 둘째, 예산 확인이 2단계(진입 Fail-fast)와 3a단계(호출 직전 원자적 예약) 두 번 일어나며 각자 역할이 다릅니다. 4단계의 SSE는 ChatGPT처럼 답변이 글자 단위로 실시간 전송되는 스트리밍 방식입니다.

기능 요구사항

F1

하이브리드 API 키 관리 및 과금

고객사는 자체 LLM API 키(BYOK)를 등록, 교체, 즉시 폐기할 수 있어야 합니다. 자체 키가 없으면 플랫폼 공용 키로 자동 연결하고, 소비된 입력·출력 토큰 기준으로 월말 청구합니다.
F2

조직 계층별 사용량 및 예산 제한

회사, 팀, 개인 단위로 분당 요청 수, 분당 토큰 수, 일·월간 예산 상한을 설정합니다. 예산의 80%에 도달하면 경고를 보내고, 100%에 도달하면 추가 호출을 즉시 차단합니다.
F3

입력·도구·출력 다계층 가드레일

입력과 출력에서 개인정보(주민번호·이메일·카드번호 등)와 프롬프트 인젝션을 차단하거나 마스킹합니다. 외부 문서나 이메일 등 도구가 가져온 결과물에 숨겨진 악성 지시(간접 인젝션)도 별도로 검사합니다.
F4

도구 연동 및 작업 상태 관리

대화 이력을 유지하며 사내 도구(Slack·Jira·DB)는 반드시 호출한 사용자 본인의 권한으로만 실행합니다. 일반 응답은 실시간 스트리밍(SSE)하고, 삭제·결제 같은 위험 작업은 사용자 승인 후 중단 지점부터 재개합니다.
F5

전 구간 이력 추적 (Observability)

모든 실행에 대해 회사, 사용자, 대화방, 턴, 개별 LLM 호출 단위로 토큰 사용량, 추정 비용, 지연 시간, 도구 실행 결과를 조회할 수 있어야 합니다.

F1은 자체 키 등록·즉시 폐기와 공용 키 월말 청구, F2는 회사·팀·개인 계층별 속도와 예산(80% 경고, 100% 차단), F3은 개인정보와 도구 반환값의 간접 인젝션 검사, F4는 호출자 본인 권한 위임과 승인 대기 후 재개, F5는 5개 식별 축 기반 전체 추적입니다.

비기능 요구사항

N1

응답 지연 기준 (성능)

게이트웨이와 입력 가드레일이 추가하는 지연은 개별 LLM 호출당 200ms 이하로 유지합니다. 도구 실행이 길어져도 사용자가 멈춘 것처럼 느끼지 않도록 진행 상태 알림을 1초 이내에 전송합니다.
N2

키 보안 및 테넌트 격리 (보안)

고객사 자체 키는 암호화해 보관하며, 로그나 추적 화면에 원문이 절대 노출되지 않아야 합니다. 키를 폐기하면 수 초 이내에 모든 서버에서 사용이 중단되고, 회사 간 대화·캐시·권한이 완전히 격리되어야 합니다.
N3

예산 통제 및 과금 정합성 (정확성)

한 사용자가 동시에 여러 요청을 보내도 월간 예산 초과 오차를 최소화해야 합니다. 공용 키 과금 기록은 개별 LLM 호출 단위로 중복 청구되거나 누락되지 않아야 합니다.
N4

장애 격리 및 가용성 (안정성)

특정 LLM 공급자에서 속도 제한(429)이나 장애가 발생해도 다른 키나 예비 모델로 자동 전환합니다. 특정 외부 도구가 응답하지 않아도 타임아웃과 차단기로 전체 챗봇 장애 전파를 막아야 합니다.

왜 공용 키 풀 설계가 필수인가요?

분당 약 2,100만 토큰은 단일 LLM API 키나 단일 계정 한도를 크게 넘습니다. 따라서 여러 API 키와 리전을 묶어 분산 호출하고, 429 오류 시 자동으로 우회하는 키 풀 구조가 반드시 필요합니다.

어느 정도 규모의 시스템인가요?

초당 수만 건이 몰리는 B2C 소셜 서비스 수준의 대규모 샤딩까지는 필요하지 않습니다. 대신 예산·과금 정합성, 키·권한 보안 격리, 장시간 비동기 상태 관리가 핵심인 B2B 엔터프라이즈 규모입니다.

계층별 속도 제한: 개인, 팀, 회사 순서로 Redis Lua 스크립트에서 분당 요청·토큰 수를 원자적으로 검사합니다. 예약 누수 방지: 응답 중 연결이 끊기거나 워커가 죽어도 만료 시간(TTL)이 지나면 예약된 예산이 자동 복구됩니다.

동기 차단 (100ms 이내 처리)
주민번호·이메일 등 개인정보를 마스킹하거나 차단합니다. 경량 분류기와 금지어 정책으로 프롬프트 인젝션을 즉시 막습니다.
비동기 탐지 및 조치 (스트리밍 지연 없음)
별도 모델로 심층 정책 위반과 단시간 토큰 폭주 패턴을 감시합니다. 이상 행위가 탐지되면 경보를 보내고 해당 가상 키를 자동 정지합니다.

[9:30 ~ 10:30] LLM은 응답이 끝나야 출력 토큰을 알 수 있어, 호출 전 추정 비용을 예약하고 완료 시 정산합니다.

[Q&A 방어 - Redis TTL] 단일 잔액 숫자에서 선차감하면 키가 만료돼도 복구가 안 됩니다. 그래서 진행 중인 예약 건을 만료 타임스탬프가 있는 Redis ZSET으로 관리해, 가용 예산 = 한도 - 확정 사용액 - 만료되지 않은 활성 예약 합계로 계산합니다.

가드레일은 100ms 이내 경량 검사만 동기 차단하고, 무거운 심층 검사·이상 탐지는 비동기로 돌려 스트리밍 속도를 지킵니다.

도구 연동과 B2B 권한·보안 격리

역할별 도구 필터링 (MCP · RBAC)

모든 도구를 모델에 한꺼번에 넘기지 않습니다. 사용자의 조직과 역할에 허용된 도구 목록만 동적으로 주입합니다.

호출자 본인 권한 위임 (OAuth)

사내 Slack·Jira·문서 DB를 공용 서비스 계정으로 호출하면 일반 직원이 임원 문서를 보는 권한 상승이 발생합니다. 반드시 요청한 사용자 본인의 OAuth 토큰을 위임받아 실행합니다.

도구 결과물 간접 인젝션 방어

외부 웹페이지나 이메일 본문에 숨겨진 악성 지시가 다음 단계를 탈취할 수 있습니다. 도구가 가져온 반환값도 신뢰할 수 없는 입력으로 보고 가드레일을 통과시킵니다.

실행 격리와 장애 차단

도구마다 타임아웃과 장애 차단기(Circuit Breaker)를 적용합니다. 코드 실행이나 브라우저 자동화 같은 고위험 도구는 컨테이너 샌드박스에서 격리합니다.
10 / 14

[10:30 ~ 11:30] B2B Agent에서 가장 자주 놓치는 두 가지 보안 포인트입니다. 첫째, 공용 서비스 계정으로 사내 시스템을 읽으면 권한 상승(Confused Deputy)이 일어나므로 반드시 호출자 본인의 OAuth 토큰을 위임(On-Behalf-Of)받아야 합니다.

둘째, 사용자가 정상 질문을 해도 도구가 읽어온 외부 문서나 이메일에 악성 명령이 숨어 있을 수 있어, 도구 결과물도 반드시 간접 프롬프트 인젝션 검사를 거쳐야 합니다.

비동기 작업 처리와 승인 대기 상태 관리

일반 대화와 짧은 도구 호출

진행 상태 알림과 답변 토큰을 실시간 스트리밍(SSE)으로 바로 전달합니다.

장시간 작업과 사용자 승인 재개

Job Queue와 비동기 Worker로 분리 실행하고, 결과는 Redis Pub/Sub로 스트리밍합니다.
1. 단계별 저장매 스텝 결과를 DB 체크포인트에 기록
2. 위험 작업 감지삭제, 결제, 외부 발송 요청 발견
3. 실행 일시 중지상태 저장 후 서버 연결 즉시 반환
4. 사용자 승인승인 이벤트를 Job Queue에 발행
5. 워커 재개상태 복원 및 토큰 갱신 후 이어서 실행
대화 메모리: 길어진 대화는 최근 이력 유지 및 과거 내용 요약
최대 스텝 제한 최대 도구 호출 제한 최대 토큰 제한

[11:30 ~ 12:30] 장애 복구용 체크포인트와 사용자 승인 대기(HITL)를 하나의 흐름으로 통합했습니다. 삭제·결제 앞에서는 승인까지 몇 시간이 걸릴 수 있어 서버 스레드를 점유하지 않고 상태를 저장한 뒤 중지했다가, 승인 이벤트가 오면 Job Queue를 통해 Worker가 복원·재개합니다.

[Q&A 방어 - 승인 대기 중 OAuth 토큰 만료] 2시간 뒤 승인 시 기존 OAuth 토큰이 만료되어 있으면, KMS에 보관된 Refresh Token으로 재개 시점에 갱신하거나 승인 이벤트에 최신 사용자 인증 토큰을 실어 보냅니다.

실전 적용 사례: LiteLLM과 Langfuse

LiteLLM Proxy

Virtual Keys로 사용자·팀별 가상 키를 발급해 원본 키를 숨깁니다. Budgets & Rate Limits로 분당 속도와 주기별 예산을 통제합니다. Spend Tracking과 Guardrails로 비용과 입출력을 제어합니다.

Langfuse

Data Model로 세션, 턴, 개별 호출과 도구 실행을 트리로 추적합니다. User Tracking으로 사용자별 호출량과 패턴을 분석합니다. Token & Cost Tracking으로 모델별 비용 대시보드를 구성합니다.
단일 장애점 (SPOF)
모든 LLM 트래픽이 프록시에 집중됩니다. 수평 확장과 DB 커넥션 튜닝이 필수입니다.
관측성 도구와 과금 원장의 분리
관측성 도구는 비동기 수집과 샘플링이 들어갑니다. 청구 원장으로 바로 쓰기엔 누락 위험이 있습니다.
키 집중 보안 경계
고객사 원본 키가 게이트웨이 DB에 모입니다. KMS 암호화와 네트워크 격리가 최우선입니다.

[12:30 ~ 14:00] 실제 프로젝트에서는 LiteLLM Proxy와 Langfuse 조합으로 빠르게 구축했습니다. 기능보다 운영하며 겪은 세 가지 한계가 핵심입니다. 프록시가 단일 장애점이 된다는 점, Langfuse 같은 관측성 도구는 과금의 원본 원장으로 바로 쓰기 위험하다는 점, 모든 키가 모이는 DB가 최우선 보안 경계라는 점입니다.
