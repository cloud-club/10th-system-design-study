# 10th-system-design-study

> 지금 잘 돌아가는 시스템을 넘어, 변화에도 버틸 수 있는 설계를 고민합니다.

## 스터디 안내

- **기간:** 2026.10.26 ~ 12.19 (8주)
- **정기 모임:** 매주 수요일 온라인, 약 1시간 · 8주차 오프라인 트래픽 버티기 챌린지
- **교재:** 『가상 면접 사례로 배우는 대규모 시스템 설계 기초 2』 · 1권은 선택 참고 자료
- **진행:** 주제 발표 → 이전 주차 설계 PR 공유 → 주중 학습 및 개별 설계
- **참여:** 개인별 발표 1회, 최소 3회 설계 · 설계 미참여 주차에는 동료 PR 리뷰

공통 요구사항을 각자의 방식으로 설계하고, 기술 선택의 근거와 트레이드오프를 함께 논의합니다.

- **모임 전:** 발표자를 제외한 모든 참여자는 해당 주제의 책 내용을 가볍게 읽어옵니다.
- **모임 중:** 발표자는 도메인 배경·핵심 개념, 요구사항, 간단한 아키텍처 설계안을 설명합니다. 도서 주제는 책을 기반으로, 자유 주제는 해당 시스템·인프라의 배경과 요구사항을 정리합니다. 자유 토론은 선택입니다. 이전 주차 설계 참여자는 제출한 PR의 핵심 내용과 고민을 공유합니다.
- **모임 후:** 설계 참여자는 발표 자료와 책을 바탕으로 설계하고, 미참여자는 자유롭게 학습하며 해당 주제의 다른 참여자 PR 전체를 리뷰합니다. 주제 선택 여부와 관계없이 희망하면 설계에 참여할 수 있습니다.

## 패키지 규칙

`week01/이름/` 형식으로 작성합니다. 개인 폴더 안의 파일명과 구성은 자유입니다.

```text
week01/
└── taehyeon/
    └── (학습 정리, 설계도, 발표 자료 등 자유롭게 구성)
week02/
└── taehyeon/
    └── ...
```

설계에는 **도메인 배경 및 핵심 개념, 요구사항 및 설계 범위, 아키텍처 설계도, 기술 선택 근거, 트레이드오프**를 포함합니다. 간단한 구현이나 검증은 선택입니다.

## PR 규칙

- 최신 `main`에서 개인 작업 브랜치를 만들고, 해당 주차의 개인 폴더에 작성합니다.
- 발표 자료와 책을 바탕으로 설계하고, **발표 이후 월요일 20시까지** `main`을 대상으로 PR을 생성합니다.
- **제목:** `[Week 02] 고태현 - 모니터링 시스템 설계`
- **본문:** 위 필수 설계 항목을 작성하거나 해당 내용을 담은 개인 폴더의 문서로 연결합니다. 구현·검증 결과와 리뷰받고 싶은 부분은 선택입니다.
- 리뷰 후 설계를 보완하고, 반영하지 않은 의견에는 이유를 남깁니다.

## 리뷰 방법

- 설계 미참여자는 **해당 주제의 다른 참여자 PR 전체를 다음 스터디 시작 전까지** 리뷰하고 피드백을 남깁니다. 설계 참여자도 자유롭게 리뷰할 수 있습니다.
- 요구사항과 제약조건을 먼저 확인하고, 기술 선택의 이유와 대안을 질문합니다.
- 트래픽 증가, 중복 요청, 장애 상황에서 설계가 어떻게 동작할지 함께 살펴봅니다.
- 개선 의견에는 근거와 예상 효과를 함께 적습니다.
- 이어서 논의할 주제는 GitHub Issue에 남깁니다.

> 예: “메시지가 중복 전달되면 어떻게 처리하나요?” · “캐시 장애 시 DB로 요청이 몰리는 상황은 어떻게 제어하나요?”
