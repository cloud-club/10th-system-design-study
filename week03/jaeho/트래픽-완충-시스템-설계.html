    선착순 티케팅
    트래픽 완충
    시스템 설계

    요청은 Kafka가 받아 두고, DB는 감당할 만큼만 꺼내 처리한다

    신재호
    00 · Queue 필요성 ① 처리량

    WEB·WAS는 초당 수만, DB는 한참 아래다

    앞단은 초당 수만 건을 받고 서버를 늘리면 그대로 늘지만, DB는 한 건씩 쓰면 초당 244건이다. 이 차이를 메우는 게 큐다.
    00 · 핵심 개념

    핵심은 물탱크 하나다 — 입구는 넓게, 출구는 일정하게

    요청은 넓은 입구로 다 받고, 출구는 Worker가 자기 속도로 연다. 입구에서 거르고(매진 캐시) 출구 끝에서 확정한다(DB).
    00 · 큐와 번호표

    번호표를 먼저 나눠 주면 N개 계산대가 서로 안 기다린다

    Partition 번호가 곧 번호표다 — 요청은 Kafka에 들어가는 순간 자기 계산대가 정해지고, 계산대마다 자기 재고만 팔아 초과 판매도 그대로 막힌다. 대가는 전체 선착순 순서가 조금 흐려지는 것.
    01 · 요구사항

    10만 명이 20초에 몰려도 지켜야 할 약속

    10만 명참여자
    20초몰리는 시간
    1만 장티켓 · 경쟁률 10:1
    초당 5천 명평균 유입 · 피크는 더 높음

    기능

    • userId로 이벤트 참여 요청
    • 재고가 있으면 즉시 202 + requestId
    • 재고가 없으면 큐 없이 바로 매진
    • requestId로 결과 조회 — 대기 · 당첨 · 매진 · 중복
    • 한 사람은 한 번만 당첨

    비기능

    • 유입이 DB보다 빨라도 수십 ms 안에 응답
    • 초과 판매 0 · 중복 당첨 0
    • 접수한 요청은 유실 0
    • 같은 메시지가 두 번 와도 한 번만 반영
    • 존 1개가 꺼져도 계속 동작
    • WAS와 Worker를 따로 수평 확장
    테스트 환경

    지금 NCP에 떠 있는 구성은 서버 6대 + 관리형 2종이다

    주황 = 접수 요청, 초록 = Worker 처리, 회색 점선 = 부하, 파랑 점선 = 관리 콘솔 지시. 부하 발생기 3대라 유입 상한은 초당 45,000. Worker는 두 존에 있지만 Kafka · MySQL은 KR-1에만 있다.
    PART 02

    아키텍처
    2개 존 이중화

    전체 지도를 먼저 보고, 요청이 지나는 다섯 구간을 하나씩 확대한 뒤, 존 하나가 꺼졌을 때를 본다.

    02 · 전체 지도

    요청은 다섯 구간을 지나 DB에 닿는다

    ①진입 ②접수 ③버퍼 ④처리 ⑤확정 — 다음 장부터 한 구간씩 확대한다. 주황 점선 = 요청, 노랑 = Kafka 복제, 회색 = DB 복제.
    02 · 접수 경로

    접수는 Kafka에 기록하는 순간 끝난다

    게이트는 전광판(재고 캐시)만 보고 판단한다. 매진이면 바로 돌려보내고, 아니면 Kafka에 기록하고 DB를 기다리지 않고 접수증(202)을 준다.
    02 · ② 접수

    쓰기는 리더 Broker 한 곳으로 가고, 복제가 끝나야 202다

    리더가 다른 존에 있으면 존을 건너 기록한다. acks=all + min.insync.replicas=2라서 복사본 2벌 이상에 써져야 접수가 끝난다.
    02 · ③ 버퍼 · Kafka 샤딩

    토픽은 24조각, 조각마다 복사본 4벌을 존마다 2벌씩

    같은 사용자는 늘 같은 Partition으로 간다. 복사본은 rack 설정으로 두 존에 2벌씩 둔다 — RF=3이면 한쪽에 2벌이 몰려 그 존이 죽을 때 1벌만 남아 쓰기가 멈춘다.
    02 · 처리 경로

    Worker는 DB 커밋이 끝난 뒤에야 다 읽었다고 알린다

    쟁반 하나가 트랜잭션 하나다. DB 왕복을 줄이려고 한꺼번에 처리하고, offset은 맨 마지막에 커밋하니 중간에 죽어도 메시지는 사라지지 않는다.
    02 · ⑤ DB 읽기 · 쓰기

    쓰기는 Master 하나로, 읽기는 Replica로 나눈다

    판정에 쓰는 잠금과 쓰기는 Master에서만 한다. 참여자 수만큼 늘어나는 결과 폴링은 Replica가 받아 Master가 쓰기에만 집중하게 한다.
    03 · 재전달과 멱등

    같은 편지가 두 번 와도 장부엔 한 줄만 남는다

    유실 대신 중복을 택했다(At-least-once). 두 번째 편지는 UNIQUE(request_id) 도장에 막히고, 이미 당첨된 요청은 SUCCESS로 다시 기록된다.

    유실 없이 받아 두고, Worker를 늘려 꺼내 가야 해서 Kafka.
    별첨 · 선착순 보장

    Broker는 3대 그대로, Partition만 1개로

    판정은 Worker 1대가 offset 순서대로. 재고 행 잠금 때문에 원래 한 줄이라 속도 손해가 적다. Partition은 줄일 수 없어 토픽을 새로 만든다.

    순서는 대기열이 앞에서 정한다

    실제 티켓 서비스들이 쓰는 방식. 순서는 대기열이, 판정은 지금 시스템이 그대로 맡는다.
