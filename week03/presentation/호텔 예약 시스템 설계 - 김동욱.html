조회 당시 재고가 같아도, 요청을 그대로 승인하면 의도하지 않은 중복 예약이 발생합니다.

문제는 두 종류입니다.

01. 같은 사용자의 중복 클릭

같은 예약 요청이 여러 번 도착 → reservation_id 멱등키로 중복 생성 방지

02. 서로 다른 사용자의 동시 요청

여기서의 중복 예약은 정책상 허용된 오버부킹과 별개07 / 11
07 / CORRECTNESSCONCURRENCY CONTROL

재고 확인과 갱신을 안전하게 묶기

일반적인 3가지 접근법 — 실제 선택은 충돌 빈도와 DB 동작에 따라 달라집니다.

PESSIMISTIC

비관적 락

SELECT ... FOR UPDATE

충돌 가능성이 큰 재고 행을 먼저 잠가 다른 트랜잭션을 대기시킵니다.

장점: 강한 직렬화 / 유의: 대기·교착
OPTIMISTIC

낙관적 락

WHERE version = :old

버전으로 충돌을 감지하고, 실패한 요청은 재조회·재시도합니다.

장점: 낮은 경합에 적합 / 유의: 재시도
DB GUARANTEE

조건부 갱신 · 제약

UPDATE ... WHERE 여유재고 ≥ 수량

재고 상한을 DB가 검사합니다. 변경 행 수와 제약 위반을 확인합니다.

장점: 단순한 최종 방어 / 유의: DB별 차이
✓

설계 원칙: 전체 숙박 날짜의 재고 갱신 + 예약 생성을 하나의 DB 트랜잭션으로 처리하고, 멱등키를 별도로 보장합니다.

조건부 갱신은 원문의 DB 제약 방식에 실무적 구현 예시를 추가한 것08 / 11
08 / CACHEREDIS VS DATABASE

Redis는 빠른 조회, DB는 최종 확정

캐시가 조금 오래된 재고를 보여줄 수 있어도, 중복 예약까지 허용해서는 안 됩니다.

Reservation
Service조회 / 예약 요청
Redis Cache빠른 잔여 재고 조회
Inventory DB정합성 최종 검증

Redis · 읽기 최적화

hotel_id · room_type_id · date로 잔여 재고를 캐싱합니다.

RDB · Source of Truth

예약 시 최종 재고 재확인과 갱신을 DB 트랜잭션으로 처리합니다.

캐시 최신화

DB 반영 후 무효화, 비동기 갱신 또는 CDC 방식으로 동기화합니다.

핵심 원칙  캐시 결과 = 예약 가능성의 힌트  ·  DB 결과 = 최종 확정
TTL은 캐시 데이터 만료를 돕지만 DB 정합성 검증을 대체하지 않음09 / 11
