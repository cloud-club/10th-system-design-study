**핵심 개념**

- **전자 지갑:** 충전한 자금을 결제에 쓰거나 같은 플랫폼의 다른 지갑으로 보낼 수 있는 서비스입니다.
- **파티션 간 이체:** 출금과 입금이 다른 파티션에서 처리될 때 한쪽만 반영된 이체를 복구할 수 있어야 합니다.
- **이벤트 소싱:** 잔액 변경을 이벤트로 기록하고 순서대로 재생해 변경 이력을 추적하고 과거 잔액을 복원합니다.

## 2. 요구사항 및 설계 범위

**기능적 요구사항**

- **지갑 간 이체 API:** `POST /v1/wallet/balance_transfer`로 출금·입금 계좌, 금액, 통화, 거래 ID를 받아 이체를 처리합니다.
- **금액 정밀도:** 정밀도 손실을 피하기 위해 금액을 문자열로 받습니다.
- **이체 멱등성:** 같은 `transaction_id`로 재시도해도 이체가 중복 반영되지 않도록 합니다.

**비기능적 요구사항**

- **처리량 및 가용성:** 초당 100만 건의 이체와 99.99% 가용성을 목표로 합니다.
- **이체 정합성:** 출금과 입금이 모두 완료되면 성공으로 응답하고, 중간에 실패하면 이미 반영한 작업을 보상할 수 있어야 합니다.
- **재현성 및 감사:** 이벤트를 재생해 특정 시점의 잔액을 복원하고 변경 이력을 추적할 수 있어야 합니다.

**추가 가정 및 제외 범위**

- **용량 추정 가정:** 이체 한 건당 잔액을 두 번 갱신하고, DB 노드 한 대가 초당 1,000건의 갱신을 처리한다고 가정합니다.
- **제외 범위:** 충전, 가맹점 결제, 환전은 설계 범위에서 제외합니다.

## 3. 아키텍처 설계도

**발표 설계도**

![전자 지갑 최종 아키텍처와 정상 이체 흐름](https://github.com/cloud-club/10th-system-design-study/blob/yeseul/week04-wallet-design/week04/yeseul/architecture.png?raw=true)

**이체 흐름 (사가 정상 경로)**

- **이체 요청 접수 (①–②):** 사용자가 A에서 C로 1달러를 이체하면, 사가 조정자가 단계별 상태 테이블에 이체 레코드를 생성합니다.
- **출금 처리 (③–⑧):** 파티션 1의 Raft 리더가 A의 출금 명령을 저장하고 검증해 이벤트를 생성합니다. 커밋된 이벤트가 CQRS 읽기 모델에 반영되면 그 결과를 조정자에게 푸시하고, 조정자는 출금 성공을 기록합니다.
- **입금 처리 (⑨–⑭):** 출금 성공을 확인한 조정자가 파티션 2에 C의 입금을 요청합니다. 파티션 2도 이벤트를 커밋하고 읽기 모델에 반영한 결과를 푸시하면, 조정자가 입금 성공을 기록합니다.
- **이체 결과 응답 (⑮):** 사가 조정자가 출금과 입금의 성공을 확인한 뒤 호출자에게 이체 결과를 반환합니다.

**설계 설명**

- **사가 조정자:** 단계별 상태를 기록하고 출금 성공 후 입금을 요청합니다. 두 단계가 성공하면 결과를 반환하고, 실패하면 완료된 작업을 역순으로 보상합니다.
- **파티션과 Raft 그룹:** 계정 ID의 해시로 파티션을 정합니다. 각 그룹의 리더가 명령을 검증해 이벤트를 생성하고 Raft로 복제합니다.
- **CQRS와 결과 푸시:** 커밋된 이벤트를 쓰기 상태와 읽기 모델에 반영합니다. 읽기 경로는 반영 결과를 역방향 프록시를 통해 조정자에게 푸시합니다.

## 4. 기술 선택 근거

- **이벤트 소싱:** 불변 이벤트를 결정론적 상태 기계로 재생해 특정 시점의 잔액을 복원하고, 같은 이력으로 코드 변경 전후의 결과를 비교합니다.
- **로컬 순차 로그와 RocksDB:** 명령·이벤트는 로컬 파일에 순차 기록하고 `mmap`으로 파일을 메모리에 매핑합니다. 잔액 상태는 쓰기에 최적화된 RocksDB에 저장해 쓰기 경로의 원격 큐·DB 접근을 줄입니다.
- **스냅숏:** 상태를 주기적으로 저장해, 복구 시 스냅숏 이후의 이벤트만 재생합니다.
- **파티셔닝과 Raft:** 단일 Raft 그룹의 처리량 한계를 넘기 위해 계정별 작업을 여러 그룹에 분산합니다. 잔액과 스냅숏은 이벤트를 재생해 복원할 수 있으므로 그룹 내 복제 대상은 커밋할 이벤트 로그로 잡습니다.
- **조정자 기반 사가:** 출금 성공 후 입금을 실행하고 실패 시 역순으로 보상합니다. 조정자가 단계별 상태를 기록해 재시작 후 진행 상황을 확인할 수 있도록 합니다.
- **CQRS와 결과 푸시:** 읽기 경로가 커밋된 이벤트로 조회 모델을 만들고, 처리 결과를 역방향 프록시로 푸시해 반복 폴링을 줄입니다.

## 5. 트레이드오프

- **Redis와 관계형 DB 샤딩:** Redis는 구조가 단순하고 수평 확장하기 쉽지만, 발표의 초기 설계는 데이터 내구성과 파티션 간 원자성을 보장하기 어렵습니다. 관계형 DB는 파티션 내부 트랜잭션을 보장하며, 다른 파티션에 걸친 이체에는 별도의 조율이 필요합니다.
- **2PC의 커밋과 락:** 참여 DB의 커밋 결정을 하나로 묶지만, 조정자의 결정을 기다리는 동안 락이 길어지고 조정자 장애 시 진행이 멈출 수 있습니다. 이기종 DB 구성에서는 참여 DB의 XA 지원도 필요합니다.
- **TC/C와 사가의 실행 방식:** TC/C는 독립적인 시도를 병렬화할 수 있어 참여 서비스가 많고 지연에 민감할 때 유리합니다. 시도·확정·취소 상태와 요청 순서 역전을 직접 관리해야 합니다. 사가는 의존 관계가 있는 작업을 순서대로 실행하며, 각 단계의 지연이 누적될 수 있습니다.
- **사가의 보상 비용:** 단계마다 로컬 트랜잭션을 끝내 락을 짧게 유지할 수 있습니다. 출금과 입금 사이의 일시적 불균형, 단계별 보상 로직과 재시도는 애플리케이션에서 관리합니다.
- **원격 저장과 로컬 저장:** 원격 큐·DB로 이벤트를 저장하면 감사 이력을 남길 수 있지만 쓰기 경로에 네트워크 왕복이 추가됩니다. 로컬 저장은 이 비용을 줄이는 대신 노드에 상태가 남으므로, 복제가 없으면 해당 노드가 단일 장애 지점이 됩니다.
- **Raft의 합의 비용:** 이벤트를 복제해 장애 복구를 지원하지만, 커밋하려면 과반수 노드의 응답이 필요합니다.
- **CQRS의 읽기 지연:** 읽기 경로를 독립적으로 확장할 수 있지만, 이벤트 반영이 늦어지면 조회 잔액이 잠시 뒤처질 수 있습니다.
