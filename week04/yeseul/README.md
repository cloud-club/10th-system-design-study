## 1. 도메인 배경 및 핵심 개념

**내용**

- **전자 지갑:** 충전한 자금을 결제에 쓰거나 같은 플랫폼의 다른 지갑으로 보낼 수 있는 서비스입니다.
- **파티션 간 이체:** 출금과 입금이 다른 파티션에서 처리될 때 한쪽만 반영된 이체를 복구할 수 있어야 합니다.
- **이벤트 소싱:** 잔액 변경을 이벤트로 기록하고 순서대로 재생해 변경 이력을 추적하고 과거 잔액을 복원합니다.

---

## 2. 요구사항 및 설계 범위

**기능적 요구사항**

- **지갑 간 이체 API:** `POST /v1/wallet/balance_transfer`로 출금·입금 계좌, 금액, 통화, 거래 ID를 받아 이체를 처리합니다.
- **금액 정밀도:** 정밀도 손실을 피하기 위해 금액을 문자열로 받습니다.
- **이체 멱등성:** 같은 `transaction_id`로 재시도해도 이체가 중복 반영되지 않도록 합니다.

**비기능적 요구사항**

- **처리량 및 가용성:** 초당 100만 건의 이체와 99.99% 가용성을 목표로 합니다.
- **이체 정합성:** 출금과 입금이 모두 완료되면 성공으로 응답하고, 중간에 실패하면 이미 반영한 작업을 보상할 수 있어야 합니다.
- **재현성 및 감사:** 이벤트를 재생해 특정 시점의 잔액을 복원하고 변경 이력을 추적할 수 있어야 합니다.

**추가 가정 및 제외 범위**

- **용량 추정 가정:** 이체 한 건당 잔액을 두 번 갱신하고, DB 노드 한 대가 초당 1,000건의 갱신을 처리한다고 가정합니다.
- **제외 범위:** 충전, 가맹점 결제, 환전은 설계 범위에서 제외합니다.

## 3. 아키텍처 설계도

**설계도**

![전자 지갑 최종 아키텍처와 정상 이체 흐름](https://github.com/cloud-club/10th-system-design-study/blob/yeseul/week04-wallet-design/week04/yeseul/architecture.png?raw=true)

**설계 설명**

- **사가 조정자:** 단계별 상태를 기록하고 출금 성공 후 입금을 요청합니다. 두 단계가 성공하면 결과를 반환하고, 실패하면 완료된 작업을 역순으로 보상합니다.
- **파티션과 Raft 그룹:** 계정 ID의 해시로 파티션을 정합니다. 각 그룹의 리더가 명령을 검증해 이벤트를 생성하고 Raft로 복제합니다.
- **CQRS와 결과 푸시:** 커밋된 이벤트를 쓰기 상태와 읽기 모델에 반영합니다. 읽기 경로는 반영 결과를 역방향 프록시를 통해 조정자에게 푸시합니다.

## 4. 기술 선택 근거

**내용**

- **이벤트 소싱과 스냅숏:** 잔액 변경 이벤트를 순서대로 재생해 과거 잔액을 복원합니다. 복구할 때는 스냅숏 이후의 이벤트만 적용해 재생량을 줄입니다.
- **로컬 순차 로그와 RocksDB:** 명령과 이벤트를 로컬 로그에 순차 기록하고 상태를 RocksDB에 저장해, 쓰기 경로의 원격 저장소 접근을 줄입니다.
- **파티셔닝과 Raft:** 계정별 작업을 여러 파티션에 분산하고, 각 파티션의 이벤트를 Raft로 복제해 노드 장애 시에도 커밋된 이력을 보존합니다.
- **사가:** 파티션 간 출금·입금의 실행 순서를 관리하고, 중간 실패 시 이미 완료한 작업을 보상합니다.
- **CQRS와 결과 푸시:** 잔액 조회를 쓰기 경로에서 분리하고, 처리 결과를 푸시해 반복 폴링을 줄입니다.

## 5. 트레이드오프

**내용**

- **2PC의 커밋과 락:** 참여 DB의 커밋 결정을 하나로 묶지만, 조정자의 결정을 기다리는 동안 락이 길어질 수 있습니다.
- **사가의 보상 비용:** 각 단계에서 로컬 트랜잭션을 끝낼 수 있지만, 출금과 입금 사이의 일시적 불균형과 보상 재시도를 관리해야 합니다.
- **TC/C의 병렬 처리:** 독립적인 시도 작업을 병렬화할 수 있지만, 시도·확정·취소 상태와 순서가 뒤바뀐 요청을 관리해야 합니다.
- **Raft의 합의 비용:** 이벤트를 복제해 장애 복구를 지원하지만, 커밋하려면 과반수 노드의 응답이 필요합니다.
- **CQRS의 읽기 지연:** 읽기 경로를 독립적으로 확장할 수 있지만, 이벤트 반영이 늦어지면 조회 잔액이 잠시 뒤처질 수 있습니다.
