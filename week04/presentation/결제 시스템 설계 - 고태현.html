추가 정의 · N4~N7은 도서 외 운영 안정성 요구사항04 / 11

이 페이지의 유량 제어, 장애 격리, 결제 이력 추적, 모니터링 및 경보는 발표에서 추가한 운영 요구사항이며 책의 요구사항으로 인용하지 않습니다.

N4는 Gateway RateLimiter와 Redis를 사용해 과도한 요청이 내부 서비스와 외부 PG에 전달되지 않게 하는 예시입니다. 정책에 따라 사용자 또는 판매자 단위의 제한을 고려할 수 있습니다.

N5는 결제 실행자가 PG를 호출할 때 연결 시간 제한과 Circuit Breaker(Resilience4j)를 적용합니다. PG 장애 중에도 결제 조회나 내부 원장 서비스가 함께 고갈되지 않도록 호출을 격리합니다. 재시도 가능한 오류만 Kafka 재시도 토픽으로 보냅니다.

N6는 payment_order_id와 event_id, trace_id를 사용해 상태 변경과 실패 원인을 남기는 감사 추적 요구사항입니다. 환불은 책에서 이번 기본 범위로 확정한 기능이 아니므로 추가 설계 범위로 소개합니다.

N7은 결제 성공률, 외부 PG 지연, HTTP 오류, 재시도 토픽 적체량 등을 지표로 관리하고 CloudWatch로 알람을 구성하는 예시입니다. 예시의 429 응답과 p95 지연은 동작 설명용이며 특정 운영 임계값을 정한 것은 아닙니다.

책의 결제 서비스(payment service)는 결제 이벤트를 수락하고 흐름을 조율하며, 결제 실행자(payment executor)는 개별 결제 주문을 PG/PSP에 요청합니다. Spring Cloud, Kafka, AWS 제품 선택은 책의 필수 기술이 아니라 발표자가 추가한 MSA 구현 예시입니다.

외부 사용자 요청은 CloudFront와 WAF, ALB를 거쳐 Spring Cloud Gateway로 들어옵니다. PG/PSP의 웹훅은 공개 ALB에서 받아 Gateway가 Payment Executor의 웹훅 처리 경로로 라우팅합니다. Executor를 외부에 직접 노출하지 않으며, 웹훅 서명과 재전송 멱등성을 검증합니다. Gateway는 Eureka 서비스 디스커버리를 이용하고 Spring Cloud Config Server가 공통 설정을 공급합니다. 애플리케이션과 공통 서비스는 ECS Fargate에서 실행한다고 가정합니다.

Payment Service는 자신이 소유한 Aurora Payment DB에 결제 이벤트·주문을 저장합니다. 결제 실행자는 별도의 Aurora Execution DB에 PG 실행 상태와 Outbox 이벤트를 같은 트랜잭션으로 저장합니다. Outbox Publisher는 커밋된 Outbox 레코드를 읽어 Amazon MSK Kafka에 발행합니다. 지갑 서비스와 원장 서비스는 별도 소비자 그룹으로 이벤트를 받고 각자 소유한 Aurora Wallet DB와 Ledger DB를 갱신합니다. 메시지 중복 소비와 서비스 간 일시적 불일치에 대응하기 위해 멱등성 및 조정이 필요합니다.

일시적인 PG 호출 오류는 Kafka 재시도 토픽으로 처리하고 반복 실패는 DLT에 기록합니다. Kafka 자체가 외부 PG 결제의 정확히 한 번 효과를 보장하지는 않으므로 payment_order_id 및 PSP nonce 멱등 검사가 필수입니다.

조정 서비스는 PG/PSP에서 받은 S3 정산 파일과 Payment·Ledger·Wallet 서비스의 조회 API를 통해 얻은 기록을 대조합니다. 다른 서비스의 운영 DB를 직접 수정하지 않으며, 조정 결과는 별도 Aurora Recon DB에 관리합니다. EventBridge Scheduler가 Spring Batch 작업을 예약하고 CloudWatch로 실패를 감시합니다. 대금 정산(pay-out)은 9페이지에 별도 흐름으로 소개합니다.

책의 그림 11.4에 등장하는 외부 결제 페이지 흐름을 요약했습니다. 결제 등록 요청에는 금액, 통화, 만료일, 리디렉션 URL, 비중복 난수(nonce)가 포함되며 PSP는 토큰을 반환합니다.

사용자는 PG/PSP의 외부 결제 페이지에서 신용 카드 정보를 입력합니다. 결제 이후 브라우저는 리디렉션 URL로 이동하고 PSP는 비동기적으로 웹훅 URL에 결제 상태를 통지합니다.

MSA 구현에서는 결제 서비스와 결제 실행자가 동기 통신하여 최초 PG 등록과 토큰을 받아옵니다. 웹훅 처리 후 Payment DB 상태 및 Outbox 이벤트를 같은 트랜잭션으로 기록하고 Kafka에 결제 완료 이벤트를 발행합니다. Wallet, Ledger 서비스는 각각 소비자 그룹으로 이벤트를 받아 독립 DB를 갱신합니다. Outbox 릴레이는 추가 구현 요소입니다.

책의 표 11.3과 11.4에서는 결제 이벤트와 결제 주문 두 테이블을 정의합니다. checkout_id는 한 번의 결제 행위를 식별하며 payment_order_id는 개별 결제 주문을 식별합니다. 하나의 결제 이벤트는 여러 결제 주문을 가질 수 있습니다.

payment_order_status는 NOT_STARTED, EXECUTING, SUCCESS, FAILED를 사용합니다. wallet_updated와 ledger_updated로 내부 서비스의 갱신 여부를 추적합니다. 책은 부동소수점 반올림 오류를 피하기 위해 amount를 string으로 보관할 것을 권합니다.

MSA 예시에서는 Payment DB는 결제 서비스가 관리하고 Wallet DB와 Ledger DB는 각각 별도 서비스가 소유합니다. 각 데이터베이스는 Aurora PostgreSQL을 사용한다고 가정합니다. 서비스 사이의 즉각적인 강한 일관성 대신 Kafka 이벤트와 조정으로 최종적 일관성을 맞춥니다. 데이터베이스 분리는 책의 필수 요구가 아닌 설계 선택입니다.

도서 · 392~396쪽 · ‘정확히 한 번 전달’은 결제 실행 결과에 대한 보장08 / 11

책은 '최소 한 번 실행'과 '최대 한 번 실행'을 함께 보장하면 주어진 연산이 정확히 한 번 실행될 수 있다고 설명합니다. 네트워크 메시지가 물리적으로 한 번만 전달된다는 뜻은 아니며, 재시도에도 결제 효과가 중복되지 않아야 한다는 의미로 발표합니다.

같은 멱등 키에 대해 데이터베이스 고유 키 제약 조건을 사용합니다. 책은 동시에 들어온 중복 요청에 429 Too Many Requests를 반환하는 예를 들고 PSP에 전달하는 payment_order_id를 비중복 난수로 사용합니다.

MSA 구현에서도 Kafka 소비자가 이벤트를 여러 번 읽을 수 있습니다. 각 서비스는 처리된 event_id 또는 payment_order_id를 고유 키로 관리하여 중복 반영을 방지합니다. Kafka 자체의 트랜잭션이나 Exactly Once Semantics만으로 외부 PG 결제의 정확히 한 번 효과가 보장되지는 않습니다.

책은 결제 지연 처리의 예로 PSP가 위험성을 검토하는 경우와 3D 보안 인증을 요구하는 경우를 듭니다. 이때 결제는 대기(pending) 상태이며 PSP는 웹훅이나 폴링으로 진행 상황을 알릴 수 있습니다.

결제 실패 처리에서는 결제 상태 추적, 재시도 큐 및 실패 메시지 큐를 설명합니다. 일시적 오류는 재시도 큐로, 여러 번 실패한 메시지는 실패 메시지 큐로 보냅니다. 재시도 간격으로 지수적 백오프를 권합니다.

MSA 구현에서는 Amazon MSK의 Apache Kafka를 사용하며, 책의 재시도 큐와 실패 메시지 큐를 Kafka의 retry 토픽과 Dead Letter Topic(DLT)으로 구현합니다. 최초 동기식 PG 요청이 일시적으로 실패하면 결제 주문을 retry 토픽에 발행하고 Spring Kafka 소비자가 같은 payment_order_id 및 PG nonce로 재시도합니다. Spring Kafka의 @RetryableTopic을 통해 소비자 처리 오류에 대한 비차단 재시도 및 DLT를 구성할 수 있습니다. Kafka가 알아서 지수적 백오프를 제공하는 것은 아니므로 Spring Kafka 설정이나 별도 지연 처리로 재시도 간격을 구현해야 합니다. 재시도 한도 초과 메시지를 DLT에 보관하여 확인합니다.

책은 복식부기 원장 시스템을 설명하면서 모든 결제 거래를 두 개의 원장 계좌에 같은 금액으로 기록한다고 소개합니다. 한쪽 계좌에서 차감되면 다른 계좌에는 같은 금액이 증가하므로 전체 합계는 0이 됩니다.

조정은 외부 PSP의 정산 파일과 내부 원장 및 지갑 데이터를 비교해 불일치를 확인하는 마지막 방어선입니다. 책은 자동 조정 가능한 문제, 수동 수정이 필요한 문제, 분류할 수 없는 문제로 나눕니다.

MSA 예시에서는 PG/PSP로부터 받은 정산 파일을 Amazon S3에 저장하고 EventBridge Scheduler로 정기 ECS Fargate의 Spring Batch 조정 작업을 실행합니다. 결제, 원장, 지갑 서비스가 각각 소유한 Aurora 데이터를 서비스 API 또는 읽기 전용 정산 사본을 통해 대조합니다. 조정 서비스가 다른 서비스의 운영 DB를 직접 수정하지 않도록 데이터 소유권을 지킵니다. 불일치와 배치 실패는 CloudWatch로 감시합니다.

대금 정산 흐름에서는 외상 매입금(accounts payable) 지급 서비스 제공업체를 이용합니다.
